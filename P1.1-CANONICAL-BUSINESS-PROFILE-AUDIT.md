# P1.1 CanonicalBusinessProfile Architecture Audit

**Repository:** `notbeingsuraj/Webloom`
**Audit Date:** 2026-09-08
**Scope:** Strictly P1.1 — representational audit only. **No production code changed.**
**Finding classification used:** `VERIFIED` (confirmed by code + tests), `INFERRED` (supported by code reading but not executed), `UNKNOWN` (cannot be established from the repo).

---

## 1. Executive Verdict

**Webloom currently has: C. fragmented business representations** — with a partial, inconsistently-enforced canonical model layered on top.

**Evidence:**

- There are **at least four distinct but overlapping business "shapes"** in active use, produced and consumed by different parts of the pipeline: the `BusinessProfile` nested `data` graph, the `BusinessProfile.toObject()` dotted-path shape (`identity.name`, `contact.phone`), the canonical **flat profile** shape (`business.name`, `contact.phone`, `location.full_address`) consumed/emitted by providers, and the `BusinessEntity` DB row (`canonical_name`, `canonical_phone`, …) in `apps/api/src/db/schema.js`.
- The **canonical runtime object** is `apps/api/src/services/BusinessProfile.js` (provenance-tracked), and the **canonical persisted object** is `BusinessEntity` (`business_entity` table). **These two are not the same shape and are bridged only by ad-hoc accessors** (`BusinessResearchService._canonicalName/_canonicalAddress/_canonicalContact/_canonicalCoordinates`) that each read multiple possible field paths defensively — a symptom of shape fragmentation.
- Providers do **not** agree on shape: `GeoapifyProvider` emits the flat `business.*` shape via `ProviderAdapter.mapGeoapifyFeatureToProfile`, while `WebExtractionProvider` emits the dotted-path `BusinessProfile.toObject()` shape (`identity.name`). `EntityResolution.calculateMatchScore` reads `identity.name`/`name` but **does not read `business.name`**, so the two provider shapes are not equivalent at the resolution boundary. **VERIFIED by execution** (see §4).
- **No single source of truth for business identity.** Several components can define or mutate name/address/phone/URL: `BusinessDataExtractor`, `OfficialWebsiteProvider`, `BusinessResearchService._mergeCanonical`, `CanonicalizationService`, `IdentityRepository`, and the AI-enrichment path.
- **AI-generated data can overwrite authoritative/hard-identifier facts** (name/website/phone/address) in the primary web-extraction path — see §8. This is a **P0 architecture issue**.

**Bottom line:** A `CanonicalBusinessProfile` is genuinely needed, but it must be introduced behind a boundary, not as another shape bolted onto the existing four.

## 4. Identity Resolution Audit

**How identity currently works:**

1. **Provider-specific identity first.** `IdentityRepository.createEntityWithProviderIdentity` creates a `BusinessEntity` and maps it to `(provider, providerRecordId)` with a UNIQUE constraint. The provider record ID (Google `placeId`/`cid`, or the source URL) is the **primary lookup key**.
2. **Stable internal ID exists:** `BusinessEntity.entity_id` (`ent_…`, generated in `IdentityRepository.createEntity`), stored on the profile via `profile.setEntityId`.
3. **Cross-provider resolution** happens only in `_persistIdentity` when a *secondary* (usually web-extraction) observation exists for an unseen `(provider, providerRecordId)`: it runs `calculateMatchScore(primary.record, secondary.record)` and, if `matchType === 'same_entity' && matchScore >= 0.85`, maps the secondary to the primary's entity; otherwise it creates a **distinct entity**.

**Identifiers considered:**

| Identifier | Authoritative? | Used in `calculateMatchScore`? |
|---|---|---|
| `entity_id` | Yes (internal, stable) | No (it IS the identity target) |
| `(provider, providerRecordId)` | Yes (unique persist key) | N/A (used as lookup) |
| `place_id` / `cid` | Shared, high-weight (0.40/0.35) | Yes |
| phone (E.164) | Strong (0.30) | Yes, **but only if both sides normalize to a non-null value** |
| website/domain | Strong (0.25) | Yes (`normalizeDomain`, deduped) |
| coordinates | Very strong (0.30) | Yes (Haversine, 10m/100m thresholds) |
| address | Medium (0.30/0.15) | Yes (token similarity) |
| name | Strong (0.35) | **Yes in intent, but effectively NOT read for `business.*` shape** |

**Verified critical defect (P0/P1): `calculateMatchScore` misses the business name for real provider records.**

- `EntityResolution.js` reads name as `record1?.identity?.name || record1?.name` (verified, line ~330) — it **does not read `record.business.name`**.
- The actual provider shapes are `business.name` (Geoapify flat) and `identity.name` (web dotted). So when Geoapify (primary) is compared, **name is never a signal**.
- Execution confirmed: two **identical** records in `business.name` form scored **0.81 → `uncertain`** (name not scored, coverage 0.5); the same records in `identity.name` form scored **0.95 → `same_entity`** (name scored, coverage 0.75). Command + output in §13.
- This is a genuine live failure: `test_identity_integration.js` **fails** on "Geoapify + web-extraction same business → same persistent entity" and "Genuine resolution decision persists full record" — both because the same business resolved to `uncertain` and produced **two** entities. (Verified run, see §13.)

**Where identity can fail (all VERIFIED/INFERRED):**

- **Name not compared** across `business.*` vs `identity.*` shapes (verified above).
- **Phone silently nulled without a country hint.** `normalizePhone('(415) 487-2600', null)` returns `null` (verified). `calculateMatchScore` derives `country` from `record.location.country`; when a provider record lacks `country` (e.g. web record), the phone signal is dropped even though the number is a valid NANP number. This directly caused the failing test.
- **Ambiguity→separate-entity** is the safe default, but it silently creates duplicates instead of surfacing them to review in all cases (only `same_brand_different_location`/`uncertain` are queued).
- **Resolution happens *after* enrichment and merge** (LEVEL 3 merge uses Entity Resolution to decide merge, and LEVEL 6 persists). If merge contaminated the profile before resolution, the persisted entity would already carry merged values.
- **AI is currently not allowed to influence *persistence* identity** (AI only fills gaps as `inferred` and never creates an entity) — but AI **can** influence the *extracted* name/address/phone that then flows into `_canonicalName` for a newly-created entity (see §8). **This is a dangerous identity assumption.**

**Dangerous identity assumptions (explicit):**
1. `canonical_name` and `canonical_address` are NOT NULL on `BusinessEntity`, so `_persistIdentity` inserts `'Unknown Business'`/`'Unknown'` when absent — **manufacturing identity values** (VERIFIED at `BusinessResearchService._persistIdentity`).
2. The web record's `provider_record_id` is the **source URL**, not a stable ID — so two different Google Maps URLs for the same business create **two distinct provider identities** that may or may not merge.
3. `calculateIdentityStrength` in `AcquisitionResult.js` treats a strong name+phone+address as `derived` identity, but this is about *evidence strength*, not a stable internal ID.

## 5. Normalization Audit

**Centralization status:** normalization is **partially centralized** in `apps/api/src/services/FieldNormalizer.js` (Phase 20 canonical normalizers) with delegation from `EntityResolution.js`. Some normalization is **coupled to Google Maps behavior** (see below).

### `utils/urlNormalizer.js` (source-URL normalizer)

- **Input:** any URL string. **Output:** deterministic canonical URL (strips fragment, removes tracking params, folds `www.`/`google.com`→`maps.google.com` for maps paths, reorders query params, normalizes trailing slash).
- **Callers:** `GoogleMapsUrlParserProvider.normalizeUrl` and `SourceCache.normalizeUrl`. **VERIFIED** — it is genuinely the single shared path.
- **Deterministic:** Yes. **Idempotent:** Yes (documented and structurally guaranteed).
- **Provider-specific coupling:** **Yes.** It has Google-Maps-specific logic baked in (`GOOGLE_MAPS_HOSTS = {maps.google.com, www.google.com, google.com}` and `GOOGLE_MAPS_PATH = /^\/(maps|place|search)/`). So the *generic* source-URL normalizer is coupled to Google Maps host folding. **INFERRED impact:** for a non-Google source URL (e.g. a directory listing), there's no special folding, which is fine; but the coupling means the "canonical source URL" concept is implicitly Maps-centric (also see SourceCache's `web_extraction` provider label).
- **Information loss:** Tracking params dropped deliberately (correct for cache-key identity). Query params preserved but lowercased for sorting — **`parsed.searchParams` key case is lowercased**, so a case-sensitive business param could change identity semantics (low risk, P3).
- **Safe for identity comparison?** Yes for source/cache-key identity; it is *not* a business-identity normalizer.

### Field-level normalizers (`FieldNormalizer.js`)

| Normalizer | Input | Output | Deterministic | Provider-specific? | Info loss | Identity-safe? |
|---|---|---|---|---|---|---|
| `normalizePhone(value, countryHint)` | raw string/number | E.164 or `null` | Yes | No (uses libphonenumber) | **Returns null for ambiguous local numbers without country** → information lost | **Partial — returns null instead of preserving value** (see §4) |
| `normalizeWebsite(value)` | URL string | canonical `https` href | Yes | No | strips fragment | Yes |
| `normalizeDomain(value)` | URL | lowercase hostname w/o `www.` | Yes | No | lowercases + strips path | Yes (for domain matching) |
| `normalizeAddress` / `normalizeAddressTokens` | address string | token list with street-type expansion | Yes | No | expands abbreviations; strips `.,#` | Yes (canonicalized tokens) |
| `normalizeCoordinates(value)` | object/array/string | `{lat,lng}` numbers | Yes | No | rejects invalid ranges → null | Yes |
| `normalizeCategories` / `normalizeServices` / `normalizeSocialLinks` / `normalizeHours` | varied | canonical arrays/maps | Yes | No | dedupes, trims | N/A (non-identity) |

**Verification:** `test_phase20_foundation.js` passes 32/32 including "equivalent formats normalize identically" for coordinates, address abbreviation expansion, and phone/website/double-count fixes. **VERIFIED.**

**Key normalization issues:**
- `normalizePhone` **drops** a valid NANP number when no country hint is available (returns null). Since `calculateMatchScore` uses the presence of a normalized phone as a *signal*, an un-normalizable-but-present phone silently reduces evidence coverage rather than being treated as "present but inconclusive". **VERIFIED.**
- There are **two phone/address-domain conceptual paths**: `EntityResolution.normalizePhone/normalizeWebsite/normalizeAddressTokens` are thin delegators to `FieldNormalizer` (good — no divergence). `CanonicalizationService.normalizeFieldValue` has its **own** small switch (name→lowercase, phone→normalizePhone, etc.) — **INFERRED duplication risk**, though it reuses `normalizePhone`/`normalizeWebsite` from `EntityResolution`.
- `data.location.coordinates` is an object, while `location.latitude/longitude` are scalars; the intelligence output references `coordinates` inconsistently across shapes.

## 6. Persistence Audit

**Database:** SQLite via Drizzle (`apps/api/src/db/schema.js`), plus a separate `SourceCache` DB (`source-cache.db`).

**Tables (business-relevant):**

| Table | PK | Key constraints | Purpose |
|---|---|---|---|
| `business_entity` | `entity_id` | `canonical_name` NOT NULL, `canonical_address` NOT NULL | Durable canonical identity |
| `provider_identity` | `id` | **UNIQUE(`provider`, `provider_record_id`)**; FK `entity_id`→`business_entity` | Maps provider record → entity |
| `resolution_record` | `id` | FK `entity_id`; enums | Historical resolution decisions |
| `source` | `id` | indexes on domain/provider | Origin of information |
| `evidence` | `id` | FK `source_id` | Supporting material |
| `claim` | `id` | FK `entity_id`; index `(entity_id, field_path)` | Statement about a field |
| `claim_source` / `claim_evidence` | `id` | join tables | Claims ↔ sources/evidence |
| `conflict` | `id` | FK `entity_id`; index field_path | Field disagreements |
| `canonical_field` | `id` | FK `entity_id`; index `(entity_id, field_path)` | Canonical field values with provenance |
| `observation` | `id` | FK `entity_id`; index `(entity_id, field_path)` | Provider observations, full provenance |
| `canonicalization_decision` | `id` | FK `entity_id`; index field_path | Canonicalization decisions |
| `review_item` | `id` | **UNIQUE `dedupe_key`**; FK `entity_id` | Human-review queue |
| `source_cache` (separate source-cache.db) | `id` | **UNIQUE(`source_hash`, `provider`)** | Provider acquisition cache |

**Can one business have multiple providers?** **Yes.** `provider_identity` allows many rows per `entity_id` (UNIQUE is on `(provider, providerRecordId)`). This is the correct multi-provider posture.

**Are provider records merged?** Provider records are **not physically merged**; they are associated to an entity via `provider_identity` and their field values are canonicalized per-field into `canonical_field`/`observation` by `CanonicalizationService`. Field-level merging is done in the `BusinessProfile` (in-memory) and re-persisted. **However**, the *entity-level* `canonical_name`/`canonical_address`/`canonical_phone`/`canonical_website` on `business_entity` are set once at creation from the primary observation and **not automatically updated** when a secondary provider adds/refines data (they remain frozen at first observation). **VERIFIED** — `createEntityWithProviderIdentity` freezes them; later observations only write `canonical_field`/`observation`. This is an inconsistency between the entity row and the canonical field store (P1).

**Is source evidence retained separately from canonical data?** **Yes, structurally:** `observation` (raw provider observations), `canonical_field` (selected canonical values), `source`/`evidence`/`claim` (source-backed evidence). **But completeness varies by write path.** `_persistIdentity` writes `observation`/`canonical_field` (via `CanonicalizationService.processObservation`) and, before that, `source`/`claim`/`evidence` are created only inside `BusinessProfile.set` (in-memory) and `processObservation`. **INFERRED:** not every path that sets a field establishes a durable `source`/`evidence` row, so evidence linkage is partial.

**Schema constraints that impede future multi-provider resolution:**

1. **`canonical_name`/`canonical_address` NOT NULL** on `business_entity` force synthetic `'Unknown'` values (P1) and force a name+address at creation even when identity is ambiguous.
2. **`provider_record_id` has no dedicated FK/semantics** — it holds placeId/cid *or* a source URL depending on provider, so "provider identity" is not a clean concept (P1).
3. There is **no `business_id` foreign key on `source_cache`** and the cache is intentionally orthogonal (documented), but there is also **no link** between a cached acquisition and the `business_entity` it produced — provenance across cache→entity is lost (P2).
4. `canonical_field.value` is `text`, not typed — numeric/coordinate values are stored as strings (`JSON.stringify` for objects via `BusinessProfile`) and `loadCanonicalFieldsIntoProfile` re-sets them with `profile.set`, which expects specific shapes. **INFERRED** risk of type drift for `location.coordinates`.
5. `Observation` allows a given `(entity_id, provider, field_path)` to accumulate unboundedly with no dedupe/weight; canonical selection relies entirely on `CanonicalizationService` logic (P2).

**Dangerous assumption:** `_persistIdentity` inserts `'Unknown Business'` / `'Unknown'` for missing `canonical_name`/`canonical_address` (VERIFIED), which then becomes a durable, resolvable identity that later real data may re-map to a different entity.

## 7. BusinessResearchService Audit

**File:** `apps/api/src/services/BusinessResearchService.js` (class exported as a singleton, `export default new BusinessResearchService()`).

**Responsibilities (it does ALL of these):**
1. **Orchestration** — `extractBusinessIntelligenceWithProviders` runs the deterministic→Geoapify→web→AI→validate→persist chain.
2. **Normalization** — builds hints, delegates field normalization, uses `sanitizeFieldValue`, merges canonical records (`_mergeCanonical`).
3. **Identity resolution** — calls `calculateMatchScore` and `_persistIdentity`, decides same/different entity, creates persistent entities.
4. **Enrichment** — `_enrichMissingWithAI` calls the AI service.
5. **Validation** — `validateBusinessProfile`.
6. **Persistence** — `_persistIdentity` directly drives `IdentityRepository` (create entity, provider identities, resolution records, review items), `CanonicalizationService`, and temporal analysis.
7. **Projection** — `_profileToIntelligence` builds the downstream payload; `regenerateCanonicalIntelligence` rebuilds from persistence.

**Accepted input:** flat input `{ googleMapsUrl?, name?, city?, state?, country?, latitude?, longitude? }` OR legacy extracted data via `extractBusinessIntelligence`.
**Returned:** `{ success, profile, intelligence, provider, validation, hints, persistence }`.

**Provider-specific assumptions (VERIFIED):**
- **Geoapify is treated as primary/authoritative**: `_persistIdentity` orders observations with Geoapify first and gives it the primary entity; web-extraction is secondary and its provider_record_id is the source URL. The provider trace and merge logic hard-code `'geoapify'` / `'web_extraction'`.
- `_buildHints` specifically parses **Google Maps URLs** (`GoogleMapsUrlParserProvider`) — if no Maps URL and no name, hints remain sparse.

**Does it mutate business identity?** **Yes.** It manufactures `'Unknown Business'`/`'Unknown'` entities and freezes canonical identity fields at first observation (see §6). It also merges provider data into the profile with `onlyIfMissing` precedence that can re-order which provider's value wins.

**Does it create canonical objects?** It creates a `BusinessProfile` (runtime canonical) and, via `_persistIdentity`/`CanonicalizationService`, durable `BusinessEntity` + `canonical_field` records (persisted canonical).

**Does AI enrichment occur inside it?** Yes — `_enrichMissingWithAI` (gap-fill, `inferred`).

**Is it a god object?** **Yes — clear god-object risk (P1).** It spans orchestration, normalization, both legacy and new extraction formats, identity resolution, persistence, canonicalization, temporal analysis, review-queue enqueueing, validation, and projection. Its dependency list is large: `BusinessProfile`, `GeoapifyProvider`, `WebExtractionProvider`, `ProviderAdapter`, `BusinessProfileValidator`, `config`, `EntityResolution`, `db/client`, `IdentityRepository`, `CanonicalizationService`, `TemporalRelocationAnalyzer`, and (dynamically) `AIService`. **Dependencies** (map):

```
routes (business, website, digitalAudit, leads)
   └─ BusinessResearchService
        ├─ BusinessProfile (runtime canonical)
        ├─ BusinessProfileValidator
        ├─ GeoapifyProvider ─ ProviderAdapter (flat shape)
        ├─ WebExtractionProvider ─ BusinessDataExtractor ─ AIService
        ├─ EntityResolution.calculateMatchScore
        ├─ IdentityRepository ─ db/client / schema
        ├─ CanonicalizationService
        ├─ TemporalRelocationAnalyzer
        └─ AIService (enrichment)
```

**Risk:** `BusinessResearchService` will be a natural habitat for future identity bugs because it silently reconciles multiple shapes and multiple responsibilities with no single owner.

## 8. AI/Enrichment Boundary

**Where AI enters (VERIFIED):**

1. **`BusinessDataExtractor.extractWithAI`** — the primary page-extraction step. It sends Google Maps page content/metadata to `AIService.generate` and expects a full structured profile (name, category, phone, website, address, coords, ratings, hours, reviews, services…). **Output is labeled `discovered`** in `extractFromGoogleMapsUrl`.
2. **`OfficialWebsiteProvider`** — fetches the official website; its `extract` output is merged as **`verified`**.
3. **`BusinessResearchService._enrichMissingWithAI`** — gap-fill only; sets fields as **`inferred`** and only when `profile.get(path) == null`.

**Fact categories currently distinguished at runtime:**
- **Observed/provider evidence** — Geoapify (`discovered`), web extraction (`discovered`), official website (`verified`), URL-parsed hints (`identified`).
- **Deterministic normalization** — `FieldNormalizer`, `urlNormalizer`, `sanitizeFieldValue` (not provenance-bearing; applied at merge/comparison).
- **Inferred** — `inferred` provenance, used only for gap-fill (category/description/services).
- **AI-generated** — the `extractWithAI` production path: AI **re-derives name/phone/website/address/coords** from the page and labels them **`discovered`**, **NOT** `inferred`.

**CRITICAL ISSUE (P0): AI-generated data can overwrite authoritative/hard-identifier facts.**

- In `BusinessDataExtractor.extractFromGoogleMapsUrl`, the AI-extracted `identity.name` (provenance `discovered`, priority 3) is written **after** the URL-parsed `identified` name (priority 2). `BusinessProfile.set`'s `provenancePriority` (verified=4 > discovered=3 > user=3 > identified=2 > inferred=1) means **the AI-extracted name replaces the URL-derived name**, including for the *persisted* entity identity.
- The **system prompt** instructs AI to "extract structured business information" — there is no hard guarantee the returned name/phone/address are faithful to authoritative data; and those values then flow into `_canonicalName`/entity creation.
- In `_mergeCanonical`, Geoapify and web extraction are both `discovered`; when Geoapify is present, `onlyIfMissing=true` preserves Geoapify — **but only in the orchestrated path**. In the **legacy path** (`extractBusinessIntelligence` on extracted data), the AI/host-page `discovered` values are merged without that protection.

**Confidence/provenance propagation:** `confidence` is passed per-field to `profile.set`, but the downstream `intelligence` object resets `confidence.overall` to a derived `0.9` when a name exists, and `_profileToIntelligence` reports provenance only inside the `_provenance` metadata block — **the facts array re-labels everything as `verified: true`** regardless of true provenance (VERIFIED at `_profileToIntelligence`, facts built with `source: 'structured_provider', verified: true`). This **overstates veracity** of values that may have come from AI extraction.

**Verdict:** AI enrichment is *positioned* as gap-fill-only in the orchestrated path, but the **primary web-extraction path lets AI write `discovered` identity fields that are treated as equal-or-superior to hard identifiers** and can seed a durable identity. This is the single most important AI/identity boundary problem to fix in P1.

## 9. Provenance Audit

**What provenance exists (VERIFIED):**
- `BusinessProfile` tracks per-field `{ value, provenance, confidence, sourceInfo, sourceId, evidenceId, retrievedAt }` with provenance categories `identified / discovered / verified / user_provided / inferred`.
- `Observation`, `CanonicalField`, `Claim`, `Evidence`, `Source`, `Conflict` tables store per-field provenance, confidence, source linkage, and temporal metadata (`temporal_retrieved_at`, `observed_at`, `last_verified_at`).
- `Conflict` records detections; `ResolutionRecord` and `ReviewItem` preserve resolution history.
- `AcquisitionResult` preserves lossless acquisition status/errors per provider.

**What is NOT preserved / where it is LOST:**

| Gap | Where it is lost |
|---|---|
| **Per-field source/evidence linkage is incomplete on some write paths** | `Source`/`Evidence`/`Claim` rows are created inside `BusinessProfile.set` and `CanonicalizationService.processObservation`, but fields set directly by `CanonicalizationService`/`loadCanonicalFieldsIntoProfile` may not get durable `Source` rows with full `when/where/confidence`. `INFERRED`. |
| **`source_urls` is a URL list, not structured provenance** | Verified page URLs are recorded, but not which *field* each URL supported, at what confidence/timestamp (`INFERRED`). |
| **Provider record identity vs entity identity conflation** | `provider_record_id` is sometimes the source URL (web) vs a stable ID (Geoapify). Once a `business_entity.canonical_*` is frozen, the *source that produced it* is only recoverable via `provider_identity`, not per-field evidence. `VERIFIED`. |
| **AI-vs-observed distinction lost downstream** | The `facts[]` array in `intelligence` relabels values as `verified:true`/`structured_provider` even when they came from AI page-extraction (`VERIFIED`, §8). The `discovered`/`inferred` provenance is only in the earlier pipeline, not the final payload consumers see. |
| **The nested `BusinessProfile.provenance` is not persisted as-is** | `BusinessProfile` provenance is durable only via `CanonicalizationService` writing `observation`/`canonical_field`. If that write path is skipped (e.g., DB unavailable — which `_persistIdentity` tolerates), provenance is lost for that run. `VERIFIED` (best-effort persistence). |
| **Cache break** | `SourceCache` caches acquisition *results* but the cache entry does not carry the business entity ID or per-field provenance, so a cache hit re-runs with fresh (possibly different) provenance. `VERIFIED` by design (cache is intentionally provenance-light). |

**Conclusion:** Webloom has a **rich provenance model** but it is **not uniformly populated** and **not consistently projected to downstream consumers**. The distinction `SOURCE FACT / INFERRED FACT / AI-GENERATED FACT / NORMALIZED FACT` exists in the schema and in `BusinessProfile`, but is **eroded at (a) the AI-extraction boundary (§8) and (b) the intelligence projection boundary** where everything is flattened/relabeled.

## 11. Target CanonicalBusinessProfile (Proposed — NOT implemented)

Minimal architecture that **supports multiple providers without forcing provider-specific fields into the canonical model**:

**Canonical identity fields** (the one true, stable, provider-independent identity):
- `entityId` (existing `BusinessEntity.entity_id`)
- Canonical `name`, `category`, primary `address`, primary `phone`, primary `website`/domain, primary `coordinates`

**Canonical business (descriptive) fields:**
- `description`, `businessType`, `secondaryCategories[]`, `hours`, `email`, `socialLinks[]`, `services[]`, `rating`, `reviewCount`, `bookingUrl` — all optional, value/provenance/confidence-annotated.

**Provider identity fields** (keep OUT of the canonical row):
- Per-provider map: `{ provider, providerRecordId, firstSeen, lastSeen, resolutionMethod, resolutionConfidence }` (this already exists as `provider_identity` — preserve it).

**Evidence/provenance model:**
- Keep `source`/`evidence`/`claim`/`observation`/`canonical_field` and **make every write path populate them**; ensure the canonical field store always has a source-backed selection.

**Enrichment model:**
- Separate `OBSERVED` (provider-recorded), `NORMALIZED` (deterministic transform), `INFERRED` (derived), `AI_GENERATED` (LLM output). AI output must be **quarantined** — never assigned provider/`discovered` provenance and never used as identity without a deterministic cross-check.

**Confidence model:**
- Per-field confidence (0–1) with a **cap for AI-generated values** (e.g. AI confidence ≤ 0.6) so AI can never outrank a hard identifier purely by provider-assigned confidence.

**Ownership:**
- **Normalization** → one module (`FieldNormalizer`), the single place all identity fields are canonicalized; no intra-consumer switches.
- **Identity resolution** → one module (extend `EntityResolution`) reading a **single canonical shape**; fix the `business.name` read.
- **Persistence** → `IdentityRepository` only; remove entity-identity mutation from `BusinessResearchService`.

**Multi-provider guarantee:** Canonical model contains **only** provider-independent fields; all `provider.*`/`placeId`/`cid`/per-provider hints live in the provider-identity and observation tables. A single `CanonicalBusinessProfile` can be reconstructed from `canonical_field` regardless of which providers were observed.

## 14. Final Verdict

- **Is a `CanonicalBusinessProfile` actually needed?** **Yes.** Webloom has at least 4 competing business shapes with inconsistent field naming (`business.name`/`identity.name`/`canonical_name`), a god-object orchestrator, and a verified identity-resolution defect that produces duplicate entities for the same business. A single canonical model/accessor removes the shape ambiguity driving these bugs.

- **What problem does it solve?**
  1. Eliminates the `business.*` vs `identity.*` resolution gap (§4) that currently produces duplicate entities.
  2. Establishes one owner for identity fields, preventing AI-generated values from silently becoming authoritative identity (§8).
  3. Provides a stable projection so downstream consumers (WebsiteGeneration, strategy) read one shape instead of many.
  4. Makes provenance uniform and queryable instead of partially-populated.

- **What should NOT be included in it?**
  - Provider-specific IDs (`placeId`, `cid`, raw provider record IDs) — those belong in `provider_identity`/observations.
  - Per-provider formatting quirks (Geoapify `categories[]`, Google `types`, `price_level`).
  - AI-generated/`inferred` descriptive content — should be quarantined, not promoted to canonical facts.
  - Raw website HTML/extraction artifacts — belong in `source`/`evidence`.

- **What should remain provider-specific?**
  - Provider record IDs, provider instances of the same business, provider confidence/authority, provider-specific categories/types, acquisition diagnostics/errors, and the raw source URL. All in `provider_identity`, `observation`, `source`, `evidence`.

- **What should be implemented first?**
  - The **two P0 fixes** that prevent data corruption now, before any broader model: (1) fix `calculateMatchScore`'s name-shape read, and (2) quarantine AI-generated identity values (§8). Followed by the P1 normalization centralization and the `CanonicalBusinessProfile` read-layer projection. **No production/storage changes were made in this audit.**
