## 4. Selected Endpoint

**Migrated endpoints:** `/api/business/analyze` (primary) **and** `/api/business/research` (its alias, same pattern, migrated together because they share one code path and both were already canonicalized in `22fe37a`).

**Why these:** they are the only `/api/business/*` endpoints with genuine business **read semantics**; they already had route integration coverage (`test_phase8_api.js`, `test_phase9_failure_modes.js`); they have the clearest benefit from canonical projection (they *are* the business-representation endpoints); and the migration does not alter the acquisition pipeline (providers, AI, persistence unchanged). `/validate-url` was left untouched — it carries no business representation. `/generate` is a website-generation endpoint, not a business-read endpoint, and consumes (rather than produces) the canonical business object, so it was out of scope for this phase.

Per §12, a second endpoint was only migrated because the pattern was already proven by the first, is the same code path, and required no architecture redesign.

## 6. Canonical Projection Integration

The route now obtains canonical business data through:

```
request
  ↓
BusinessResearchService.extractBusinessIntelligenceWithProviders(...)   [unchanged]
  ↓
result.intelligence + result.persistence?.providerIdentities
  ↓
CanonicalBusinessProfileService.fromEntityData({ record, providerIdentities })
  ↓
res.json({ business: canonical, ... metadata.analysis })
```

Concretely, in `apps/api/src/routes/business.js`:

```js
const persistedProviders = result.persistence?.providerIdentities ?? null;
const canonical = canonicalService.fromEntityData({
  record: rawIntelligence,
  providerIdentities: persistedProviders,
});
```

Key properties of this integration:

- **No acquisition logic moved into the route.** `BusinessResearchService` still orchestrates providers, entity resolution, AI enrichment, and persistence — untouched.
- **No identity resolution moved into the route.** The route only forwards what the research pipeline already produced (`result.persistence.providerIdentities`) into the projection.
- **No normalization moved into the route.** The canonical service does pure, deterministic projection of the intelligence record.
- **No AI invoked from the route** (Brand-DNA optional enrichment is pre-existing route behavior — additive and non-canonical).
- **The route never independently reconstructs canonical fields.** There is no `{ name: profile.data.name, address: ... }` anywhere. Every canonical business value (`identity.name/address/phone/website/domain/coordinates/entityId`, `business.*`, `reputation.*`) originates from the projection output.
- The route passes **provider-identity observations** through to the projection so provider IDs live in `providers[]` (Rule B).

## 7. Provider Isolation

- The projection (`extractProviderMeta`) reads provider metadata from the flat provider shape (`record.provider`), web-extraction shape (`record.source`), or persisted `ProviderIdentity` rows (`providerIdentities`), and emits `providers[]` entries: `{ provider, providerRecordId, resolutionMethod, resolutionConfidence, firstSeen, lastSeen }`.
- The route now hands `result.persistence?.providerIdentities` (the persisted observations, when the pipeline produced them) into `fromEntityData(...)`, so a persisted `geoapify → ChIJ...` mapping appears as `providers[].providerRecordId`, **never** in `identity`.
- Verified by test: `provider ID (placeId) is isolated in providers[], never identity` — asserts `placeId` absent from `identity`/`business` JSON, no `providerRecordId`/`googlePlaceId`/`geoapifyPlaceId`/`placeId` keys in identity, and the provider entry present in `providers[]` with the record id.
- When persistence was skipped (best-effort), `extractProviderMeta` still derives provider metadata from the record's own `source`/`provider` metadata — the canonical output keeps a structured `providers[]` without depending on persistence.

## 8. Identity and Provenance Safety

- **Identity safety:** `canonical.identity.name/address/phone/website/domain/coordinates` are set exclusively by the canonical projection. `canonicalName()` nulls synthetic placeholders (`unknown business`, `unknown`, `n/a`, `unnamed`, …) as defense-in-depth; missing authoritative values project to `null`, never to invented values. Verified by test `missing canonical identity stays null (never synthetic)`.
- **entityId:** only sourced from a persisted entity id / explicit record `entityId` (never a provider id).
- **AI provenance (P1.2 quarantine):** the projection preserves `ai_generated` provenance untouched (`buildAiGeneratedProvenance`, `_mergeBusinessProfileProvenance`) and never upgrades it to `verified/discovered/identified/user_provided`. AI-extracted records surface as `enrichment.aiExtracted = true` (+ `aiGeneratedFields`). Verified by test `ai_generated intelligence stays ai_generated (P1.2 quarantine)` — iterates every provenance-map entry and asserts no deterministic-tier upgrade.
- **Determinism:** the projection is pure and synchronous (`fromEntityData`), so repeated equivalent requests return equivalent canonical business output (verified by test 11).

## 9. Compatibility

- **Endpoint-specific metadata preserved:** facts, unknowns, trustSignals, positioning, digitalPresence, services, rating, reviewCount, openingHours, reviews, photos all remain available under `metadata.analysis` (and, where they are canonical business fields, also in the canonical `business` section). This follows the plan's guidance: one canonical representation for business data, not one universal response shape for every endpoint.
- **Top-level identifiers preserved:** `success`, `businessDNA`, `brandStrategy`, `metadata.providers` (provider trace), `metadata.persistence`, `metadata.validationIssues`, `metadata.extractedAt`, `metadata.cached` remain unchanged.
- **Compatibility strategy:** rather than silently maintaining two independently generated versions, the response keeps the canonical `business` block plus a separate `metadata.analysis` block. Any future legacy field must derive from the canonical profile (the plan's rule), which is what the migration does — no raw `profile.data.name` style reconstruction anywhere in the route.
- `/research`'s `data` key shape changed from raw intelligence to canonical. Since `/research` is a documented alias of `/analyze` sharing the same research pipeline, and there was no evidence of a distinct `/research`-specific external consumer relying on the raw `data` shape, the canonical layout is applied consistently. This is called out in Known Limitations (§14) as the one intentional contract-shape change.

## 14. Known Limitations

- **`/api/business/research` top-level shape change:** `data` changed from raw intelligence to canonical. No distinct external consumer was found for the raw `/research` shape; if one exists downstream, it must migrate to the canonical layout or rely on `metadata.analysis`.
- **`test_phase8_api.js` stale provider mock** (pre-existing, documented above) prevents that file from acting as a clean regression signal. It is not a P1.4 defect; aligning it is recommended in a tooling/Phase-20-follow-up.
- **The two known pre-existing canonicalization failures** remain separately tracked and are not addressed in this API-boundary phase (explicitly out of scope per §13).
- **Legacy consumers not yet migrated** to the canonical read layer (leads in-memory cache, brand-strategy route, digital-audit route, reviews route, landing-page route) — deferred intentionally; P1.4 is the `/api/business/*` boundary phase only.
- **`providers[]` when persistence skipped:** provider metadata is derived from the record's own source metadata; entries may lack `firstSeen`/`lastSeen`/`resolutionMethod` when those were persistence-only fields. Acceptable: canonical `providers[]` reflects available evidence.
