## 4. Migration Order

Consumers were migrated in this order based on risk (self-contained → low-coupling → validation-only):

1. **Leads cache** — Fully self-contained in-memory route; no downstream consumers; all fields directly traceable to business identity/contact/location.
2. **BrandStrategyService** — Standalone service method; reads identity for validation and data-quality scoring; clear canonical equivalents.
3. **DigitalAuditService** — Small surface (two field reads); website check and phone read from canonical.
4. **Website route validation** — Pure validation gate; no data transformation; minimal risk.

**Why this order:** Each migration is independently testable. Starting with the leads cache proved the canonical projection works end-to-end in a route context. BrandStrategy and DigitalAudit validated service-level integration. Website route was the lightest touch.

## 5. Leads Cache

**Before:** `routes/leads.js` read `businessData.identity?.name`, `businessData.contact?.phone`, `businessData.location?.city`, `businessData.rating`, `businessData.services` directly from the raw intelligence shape. Missing name fell back to `'Unnamed Business'`.

**After:** `routes/leads.js` projects through `CanonicalBusinessProfileService.fromEntityData({ record: businessData })`. Business identity reads come from `canonical.identity.*`, `canonical.business.*`, `canonical.reputation.*`. Analysis-specific metadata (trustSignals, facts, unknowns, digitalPresence, positioning) moved to `analysis.metrics`. Synthetic identity fallback removed — `leadName` is `null` when no authoritative name exists (P1.2 invariant).

**Key changes:**
- Removed `'Unnamed Business'` fallback
- `contact.email` now from `canonical.business.email` (was `businessData.contact.email`)
- `contact.website` now from `canonical.identity.website` (was `businessData.contact.website`)
- `openingHours` now from `canonical.business.hours` (was `businessData.openingHours`)
- Analysis metadata preserved in `analysis.metrics` with explicit null coalescing

**Tests:** 7 consumer-specific tests covering lead shape, canonical field flow, and missing-identity safety.

## 6. Digital Audit

**Before:** `DigitalAuditService` read `businessData.contact?.website` for the `hasWebsite` check and `businessData.contact?.phone` for the no-website audit.

**After:** Both reads go through `CanonicalBusinessProfileService.fromEntityData({ record: businessData })`. The `hasWebsite` check reads `canonical.identity.website`. The phone read in `generateNoWebsiteAudit` reads `canonical.identity.phone`. The `digitalPresence?.googleMapsUrl` and `source?.mapsUrl` reads remain on raw data (endpoint-specific metadata, not canonical business facts).

**Tests:** 2 consumer-specific tests verifying canonical website check and phone preservation in no-website audits.

## 7. Brand Strategy

**Before:** `BrandStrategyService.generateBrandDNA` validated `normalizedBusinessData.identity` directly. `assessDataQuality` read `data.identity?.name`, `data.identity?.category`, `data.identity?.description`, `data.location?.address`, `data.contact?.phone`, `data.contact?.website`, `data.services` directly.

**After:** `generateBrandDNA` validates through `canonical.identity.name`. `assessDataQuality` reads all identity/contact/location/service fields from the canonical projection. Analysis-specific data (`trustSignals`, `facts`) remains on the source data (not canonical). The full intelligence shape is still passed to the AI prompt builder for complete context.

**Tests:** 3 consumer-specific tests covering data quality scoring with canonical fields and empty-data behavior.

## 8. Landing Page

**Scope note:** The P1.4 report identified the `/api/website/generate` endpoint (in `routes/website.js`) as consuming business data rather than producing it. The validation gate in this route was migrated (consumer #4). No separate landing-page route exists in the repository.

**After:** Both validation checks use `CanonicalBusinessProfileService.fromEntityData({ record: ... })` and read `canonical.identity.name`. The full `businessData` object is still passed to `WebsiteGenerationService` for generation (which already uses canonical reads internally, migrated in P1.3).

**Tests:** 2 tests validating canonical name flow and missing-identity rejection in the website route.

## 9. Frontend

**Finding:** The frontend (`apps/web/src/pages/GeneratedSites.tsx`) consumes `/api/business/analyze` and accesses `business.identity.name`. This already matches the canonical projection output shape. The `AnalyzedBusiness` TypeScript interface in the frontend defines `identity: { name, category, description }`, `contact: { phone, email, website }`, `location: { address, city, state, country, coordinates }` — all consistent with the canonical projection.

**Action:** No frontend migration was needed. The API contract established in P1.4 already exposes the canonical shape, and the frontend's type definition aligns.

## 10. Provenance and Identity Safety

**P1.2 safeguards preserved across all migrated consumers:**

- **No synthetic names:** Leads cache no longer falls back to `'Unnamed Business'` or `'Unknown Business'`. Missing identity.name projects to `null`.
- **No provider ID promotion:** Provider IDs (`placeId`, `url`) remain in `providers[]` via the canonical projection. No consumer reads provider IDs as business identity.
- **ai_generated provenance survives:** Canonical projection preserves `ai_generated` provenance. BrandStrategy and DigitalAudit read through the canonical layer, which does not upgrade provenance classes.
- **Missing identity remains null:** All migrated consumers handle null identity gracefully — no consumer fabricates identity from insufficient evidence.
- **Consumer-specific metadata intact:** trustSignals, facts, unknowns, digitalPresence, positioning remain in consumer-specific sections (leads `analysis.metrics`, business route `metadata.analysis`).
