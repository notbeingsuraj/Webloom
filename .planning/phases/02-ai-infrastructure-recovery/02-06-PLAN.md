# Plan 02-06: Failure Handling and Resilience

## Objective
Implement comprehensive failure handling and resilience for the AI infrastructure.

**Requirements:**
- Provider health checks
- Circuit breakers
- Bounded retries
- Exponential backoff with jitter
- Provider-specific cooldown periods
- Quota-aware routing
- Request timeouts
- Fallback selection
- Response validation
- Failure logging
- Provider recovery detection

**Error Classification (must be correct):**
- **400**: Invalid request - Do NOT retry blindly
- **401/403**: Credentials/permissions problem - Disable affected provider until corrected
- **404**: Invalid endpoint or model identifier - Treat as configuration problem
- **429**: Rate limit or quota exhaustion - Respect retry headers and cooldown information
- **500/502/503**: Provider-side failure - Attempt another eligible provider
- **Timeout**: Bounded retry or failover
- **Malformed JSON**: Validate, attempt one controlled repair where appropriate, or switch provider

**Constraints:**
- Do not repeatedly call an exhausted provider
- Do not allow fallback loops
- Do not allow one unavailable provider to block all other providers
- Account for concurrent requests and serverless execution
- In Vercel, do not rely on in-memory circuit-breaker state as the only source of truth. Evaluate shared state through Redis or an appropriate alternative.

## Tasks

### Task 1: Enhance AIError Taxonomy
- File: `apps/api/src/services/ai/AIError.js` (existing)
- Add new error categories if needed: `COOLDOWN_ACTIVE`, `QUOTA_EXCEEDED_MONTHLY`, `CIRCUIT_OPEN`
- Ensure `classifyAIError` correctly maps all HTTP statuses and error messages
- Add provider-specific error patterns (NVIDIA, Hugging Face, DeepSeek)
- Verify `parseRetryAfterMs` handles all provider Retry-After formats
- Add `parseAffordableMaxTokens` for NVIDIA/HF/DeepSeek 402 responses

### Task 2: Implement Circuit Breaker
- File: `apps/api/src/ai/CircuitBreaker.js`
- States: CLOSED (normal), OPEN (failing), HALF_OPEN (testing recovery)
- Config per provider: failureThreshold (default 5), successThreshold (default 2), timeout (default 60s)
- Methods: `execute(operation)`, `getState()`, `reset()`, `recordSuccess()`, `recordFailure()`
- Per-provider instances stored in ProviderHealthMonitor
- Prevent fallback loops by tracking circuit state in fallback selection
- Redis-backed state for serverless (Vercel) - use Upstash Redis or similar

### Task 3: Implement Retry Controller
- File: `apps/api/src/ai/RetryController.js`
- Exponential backoff with jitter: `base * 2^retry + random(0, 250ms)`
- Provider-specific cooldown periods (respect Retry-After header)
- Bounded retries: maxAttempts per provider (configurable, default 2)
- Respect total request budget (maxTotalMs from config)
- Methods: `executeWithRetry(operation, options)`
- Options: maxAttempts, baseDelay, maxDelay, jitter, retryableCategories, deadline

### Task 4: Implement Provider Health Monitor
- File: `apps/api/src/ai/ProviderHealthMonitor.js`
- Track per-provider: consecutiveFailures, lastSuccess, lastFailure, avgLatency, errorRate, cooldownUntil, circuitBreakerState
- Methods: `recordSuccess(provider, latency)`, `recordFailure(provider, error)`, `isHealthy(provider)`, `getCooldown(provider)`, `getStats(provider)`
- Health criteria: errorRate < 0.5, consecutiveFailures < threshold, not in cooldown, circuit CLOSED
- Integrate with AIHealthService for health check probes
- Redis-backed for serverless persistence

### Task 5: Implement Quota Manager
- File: `apps/api/src/ai/QuotaManager.js`
- Track per-provider: monthlyBudgetUSD, currentMonthUsageUSD, dailyUsageUSD, requestCount, tokenCount
- Methods: `canAfford(provider, estimatedTokens, model)`, `recordUsage(provider, tokens, cost)`, `getRemainingBudget(provider)`, `resetMonthly()`
- Configurable monthly spending limits per provider
- Alert at 80% and 95% of budget
- Allow paid providers to be disabled entirely via config
- Cost estimation: use provider pricing or model costPer1MTokens from ModelRegistry

### Task 6: Implement Fallback Controller
- File: `apps/api/src/ai/FallbackController.js`
- Prevent fallback loops: maxFallbackDepth (default 3), track fallback chain
- Select next best provider based on: capability match, health, cost, latency
- Methods: `selectFallback(failedProvider, capability, context)`, `recordFallback(fromProvider, toProvider, reason)`, `canFallback(capability, context)`
- Context: attemptedProviders[], fallbackDepth, maxCost, maxLatency
- Never fallback to a provider in cooldown or with OPEN circuit

### Task 7: Implement Request Timeout Handling
- Per-request deadline from orchestrator (maxTotalMs)
- Per-provider timeout from config (provider.timeoutMs)
- Clamp timeout to remaining budget
- On timeout: record failure, trigger circuit breaker, attempt fallback
- Never exceed total budget across all providers and retries

### Task 8: Implement Response Validation and JSON Repair
- File: `apps/api/src/ai/OutputValidator.js`
- Validate structured output against JSON Schema
- For models without native structured output (Nemotron):
  - Extract JSON from prose using regex/schema-guided parsing
  - Attempt one controlled repair: re-prompt with schema + invalid output
  - If repair fails, switch provider
- Methods: `validate(output, schema)`, `extractJSON(text, schema)`, `repair(output, schema, errors)`

### Task 9: Implement Failure Logging
- Structured logging for every failure
- Log: requestId, capability, provider, model, errorCategory, httpStatus, safeMessage, latency, attempt, fallbackDepth, circuitState, cooldownRemaining
- No secrets in logs (use existing sanitizeSecretText)
- Correlation IDs for tracing request across providers

### Task 10: Implement Provider Recovery Detection
- Periodic health probes for providers in cooldown/OPEN circuit
- Probe interval: exponential backoff (30s, 60s, 120s, 300s, max 10min)
- On probe success: transition HALF_OPEN → CLOSED after successThreshold
- On probe failure: extend cooldown, stay OPEN
- Configurable probe parameters per provider

### Task 11: Redis/Shared State for Serverless
- Evaluate Upstash Redis, Vercel KV, or Cloudflare KV for shared state
- Implement state adapter interface: `get(key)`, `set(key, value, ttl)`, `increment(key)`, `expire(key, ttl)`
- Circuit breaker state, cooldown timestamps, quota counters in shared store
- Fallback to in-memory with warning if Redis unavailable
- Document Vercel deployment requirements

### Task 12: Integration Tests for Resilience
- Test circuit breaker: OPEN after threshold, HALF_OPEN probe, CLOSED after success
- Test retry: exponential backoff, jitter, Retry-After header respect
- Test cooldown: provider in cooldown not selected for fallback
- Test fallback loop prevention: max depth enforced
- Test quota: provider disabled at budget limit
- Test timeout: request fails at deadline, fallback attempted
- Test JSON repair: malformed output repaired or provider switched
- Test recovery: provider returns to healthy after cooldown
- Test concurrent requests: shared state consistency under load
