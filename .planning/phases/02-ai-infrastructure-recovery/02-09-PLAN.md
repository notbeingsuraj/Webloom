# Plan 02-09: Health Monitoring

## Objective
Implement a meaningful `/health/ai` endpoint that provides comprehensive visibility into AI infrastructure health.

**Must Expose:**
- Provider configuration status
- Provider availability
- Model identifiers
- Last successful request
- Last error
- Latency (p50, p95, p99)
- Failure rate
- Cooldown state
- Quota state (where available)
- Active provider per capability
- Fallback status

**Constraints:**
- No secrets exposed
- Configured API key ≠ healthy provider
- Include provider-level diagnostic command/endpoint for independent testing

## Tasks

### Task 1: Enhance AIHealthService
- File: `apps/api/src/services/ai/AIHealthService.js` (existing)
- Extend four-fact health model with:
  - Latency percentiles (p50, p95, p99) from telemetry
  - Failure rate (last 100 requests)
  - Cooldown state (remaining seconds)
  - Quota state (remaining budget, percentage used)
  - Circuit breaker state (CLOSED/OPEN/HALF_OPEN)
  - Active provider per capability (from CapabilityRouter)
  - Fallback status (depth, last fallback reason)
- Cache results with configurable TTL (default 30s)
- Collapse concurrent checks to single probe

### Task 6: Provider-Level Diagnostic Endpoint
- New endpoint: `GET /health/ai/diagnose?provider=openrouter`
- Runs independent health probe for specific provider:
  - Configuration validation
  - Network reachability (DNS, TCP connect)
  - Authentication test (probe with minimal tokens)
  - Model availability check (list models or test completion)
  - Latency measurement (3 samples)
  - Returns detailed diagnostic report
- Also support: `POST /health/ai/diagnose` with custom test prompt
- Rate limited (10/min) to prevent abuse

### Task 7: Capability Health Summary
- Add capability-level health to `/health/ai`:
  - Active provider per capability
  - Fallback chain status
  - Estimated cost per request
  - Latency SLA compliance
- Derived from CapabilityRouter and ProviderHealthMonitor

### Task 8: Configuration for Health Checks
